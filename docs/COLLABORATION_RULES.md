# 双方协同检查与 Bug 修复规则

本仓库后续固定采用“双重检查”流程。

## 角色分工

### A. 实现方
- 编写或修改功能
- 先做本地/静态自检
- 记录已知限制与未验证项
- 不把“语法通过”写成“真机通过”

### B. 复核方
- 独立检查改动
- 查找逻辑错误、运行风险、同质化风险、边界条件和回归问题
- 对高风险点提出复现步骤
- 修复后再次回归检查

## 固定流程
1. Issue 记录问题或目标
2. 建 feature/fix 分支
3. 实现修改
4. 第一轮自检：语法、结构、关卡数据、占位符、资源路径
5. 第二轮独立复核：玩法逻辑、Cocos 启动、UI、输入、存档、生命周期、异常恢复、相似度
6. 发现 Bug 后修复
7. 再跑回归测试
8. 建 PR，写明“已验证”和“未验证”
9. 只有通过复核后才合并 develop/main

## Bug 优先级
- P0：无法启动、灰屏、崩溃、存档损坏、核心玩法不可用
- P1：关卡无法完成、输入卡死、广告/生命周期异常、严重同质化
- P2：UI错位、动画异常、提示不清、轻微兼容问题
- P3：体验优化与非阻断问题

## 验收原则
- Cocos Creator 未实际预览：不得写“Creator 已通过”
- 抖音开发者工具未构建：不得写“抖音构建已通过”
- 未真机验证：不得写“真机已通过”
- 自动启发式可解性：不得冒充 180 关真实通关
- 内部相似度：不得冒充抖音官方算法或阈值

该规则适用于六款小游戏的后续开发、修复、去同质化和上架前验收。
